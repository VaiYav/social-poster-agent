# 03 — Надёжность постинга и анти-бан

Фокус: «опубликовать ровно один раз», устойчивость browser-automation, риск банов. Опирается на
внешний ресёрч (источники — в конце и в `05`). Только проблемы и предложения.

---

## 1. «Ровно один раз» сейчас не гарантировано

Постинг **неидемпотентен** (нельзя «повторить тот же POST» безопасно), а вокруг него стоят ретраи и
self-recovery. Это классический источник дублей. Складывается из:

1. **`jobId=postId` — поверхностная идемпотентность.** Дедуп BullMQ держится только пока job в Redis;
   `removeOnComplete:{count:100}` (`queue.factory.ts:102`) вытесняет старые → повторный enqueue того
   же `postId` создаёт новый job. Реальная защита — статус-guard POSTED/POSTING
   (`posting.service.ts:68-73`). BullMQ — **at-least-once**, не exactly-once (см. источники).
2. **Stalled-job → повторный прогон.** BullMQ переотдаёт job при истечении lock (`lockDuration`, по
   умолчанию 30с) если воркер не продлил lock. Длинный пост (человекоподобный ввод + задержки +
   self-recovery 5/10/20с) может это спровоцировать. Дубль смягчается guard-ом POSTING — но именно
   он создаёт следующую проблему.
3. **«Orphaned POSTING».** Статус POSTING ставится до браузерной работы (`posting.service.ts:95`).
   Краш процесса/браузера в середине → пост навсегда в POSTING. Reconciliation чинит только APPROVED
   (`health-monitor.service.ts:81-140`); stuck-POSTING **только считается** в алерте (`:308`), не
   восстанавливается. Guard POSTING блокирует повторную отправку → пост «потерян».
4. **Self-recovery повторяет постинг.** При ошибке `/not logged in|session expired|relogin/i`
   `posting.service.ts:204-274` повторяет `postFn()`. Если сабмит реально прошёл, а ошибка лишь похожа
   на relogin — **повторная публикация**.
5. **Мёртвый `withRetry`.** Постеры не бросают (`x.poster.ts:288-295` → `{error}`), поэтому
   `withRetry(postFn, {retryable})` (`posting.service.ts:165`) никогда не срабатывает. Ретрай
   прикручен не к тому слою.

### Что нужно (must-have из ресёрча)
- **Верификация факта публикации перед любым ретраем.** «Fire and assume success» — неверно. Перед
  повтором — перечитать timeline / поймать возвращённый permalink. (BullMQ docs: stalled/at-least-once;
  Stripe/Bravenewgeek: exactly-once недостижимо без идемпотентного ключа на стороне эффекта.)
- **Идемпотентный ключ на уровне доменной операции** (не только `jobId`): «для этого `postId` уже есть
  опубликованный permalink → не публиковать».
- **Reaper для stuck-POSTING:** по таймауту проверять, появился ли пост (permalink/timeline) →
  POSTED либо FAILED+re-enqueue. Сейчас его нет.

## 2. Детекция факта публикации — самое слабое звено

Детекция успеха **хрупкая в обе стороны** (подробно `02 P1/P2`):
- `validatePostOnProfile` (`base.poster.ts:155-225`) — `innerText.includes(content.slice(0,40))` +
  «первая `/status/`-ссылка». Ложный POSTED (старый похожий твит) и ложный FAILED (эмодзи/кириллица/
  реформат ссылок).
- `verifyPostVisible`/`detectPostShadowban` (`base.poster.ts:458,507`) на `networkidle`, которого на
  X/Threads нет → всегда таймаут → молча `false`.

Для постера, который **пишет** (а не читает), это критично: на детекции успеха висит и
идемпотентность, и метрики, и решение о ретрае.

**Fix:** ловить нативный permalink немедленно после сабмита (тост/редирект/ответ сети), нормализовать
текст (учесть t.co, эмодзи, кириллицу), URL принимать только с совпадающим хэндлом, проверки — на
`domcontentloaded`+`waitForSelector`.

## 3. Анти-бан: три оси, закрыта только одна

Ресёрч разделяет три независимые оси детекции. Их нельзя смешивать.

### Ось A — fingerprint/CDP (закрыта Camoufox, **частично устарела как аргумент**)
Camoufox патчит Firefox на C++ (MIT, Juggler вместо CDP) — снимает статический fingerprint/CDP-вектор.
Но: классический CDP-сигнал «умер сам» ~май 2025 (V8-коммиты), у Camoufox ~год паузы в поддержке и
beta-сборка (v146 beta, янв 2026); сам Firefox-TLS-shape — это тоже отпечаток. То есть исходное
обоснование «выбрали Camoufox, чтобы убить CDP-вектор» в 2026 ослабло. Защищает от **статики**, не от
поведения/IP.

### Ось B — IP/сеть (**НЕ закрыта** — главный пробел)
- `CAMOUFOX_PROXY_URL` — **один статический прокси на весь браузер** (`browser.factory.ts:92`); если
  он не задан — постинг идёт с IP сервера (часто datacenter), что само по себе поднимает fraud-score
  до 50–85 ещё до первого символа.
- `PROXY_ROTATION_ENABLED` существует как флаг, но фактически ротации/липкости per-account нет.
- **Один общий браузер на X и Threads** (`getBrowser()`, `browser.factory.ts:78-105`) → один
  browser-level fingerprint и один IP на разные аккаунты/бренды → они **связываются** между собой.
  Meta кросс-линкует баны между FB/IG/Threads.
- Прокси с timezone, не совпадающим со спуфнутой локалью, по ресёрчу **хуже**, чем без прокси.

**Это важнее любого fingerprint-tweak.** Must-have: residential/mobile sticky-proxy, один
IP+fingerprint на один аккаунт, согласованные timezone/locale/IP.

### Ось C — поведение/скорость (частично сломана)
- Рейт-лимиты постинга консервативны (1/день дефолт) — это плюс, но **engagement-лимиты сломаны до
  1/день** (`02 R1`), то есть «человекоподобная активность» как анти-бан-мера не работает.
- Engagement открывает отдельную навигацию на каждый пост (`02 EN1`) — наоборот, бот-паттерн.
- Auto-login формой на лету (`02 SE1`) — по ресёрчу это главный триггер «suspicious login».
- Конкретные «безопасные» числа действий/день — это **вендорский фольклор**, часто
  противоречивый; брать минимальные как потолок, не как цель.

## 4. Сессии и логин

- **Cookie-first есть** (`sessions.service.ts:164-188`) — это правильно (cookie-auth стабильнее
  формы). Но при провале cookie — форма-логин **каждый раз**, синхронно внутри постинга
  (`posting.service.ts:232`). Логин — самое банабельное действие; делать его в момент публикации
  рискованно.
- Race на параллельный логин (`02 SE2`).
- Detection «разлогинены» (`base.poster.ts:335-359`) — по URL + набор DOM-индикаторов; набор
  захардкожен и устареет с редизайном (особенно X-оверлей без смены URL).

**Fix:** вынести ре-логин в отдельный контролируемый процесс с бэкоффом, длинным cooldown и алертом;
не логиниться синхронно в постинге; per-network инфлайт-мьютекс.

---

## 5. Селекторы и браузерные ресурсы

- **Нет единой fallback-цепочки в скрейпинге** (тренды `[data-testid="trend"]` без fallback,
  `02 TR2`), хотя в постинге цепочка `data-testid→role→label→css→text` есть. X churn-ит `data-testid`.
- **`fullPage` скриншоты без очистки** (`02 P7`) — disk-leak и лишняя латентность на каждом шаге.
- **`networkidle` там, где его нет** (`02 P2`) — таймауты 15–30с, замаскированные под «нет данных».
- **Пул контекстов не инвалидируется при пересоздании браузера** (`02 P6`).
- **FB — один persistent-context на всё** (`02 P5`) — гонки страниц при параллельных FB-операциях.

---

## 6. Расписания, которые тихо останавливаются

- **Engagement** перестаёт планироваться после дня 1 (`02 EN6`) — нет полуночного крона.
- **Recycling** не запускается автоматически вовсе (`02 RC2`).
- Это «тихие смерти»: процесс жив, фича — нет; мониторинг (`getStatus`) ещё и врёт (всегда 0).

## 7. Чеклист анти-бан-контролей (must-have vs nice-to-have) и статус SPA

| Контроль | Класс | Статус в SPA |
|----------|-------|--------------|
| Верификация факта публикации перед ретраем | **MUST** | ✗ хрупкая (`02 P1/P2`) |
| Идемпотентный ключ доменной операции (не только jobId) | **MUST** | ✗ |
| Reaper для stuck-POSTING | **MUST** | ✗ (только алерт) |
| Residential/mobile sticky-proxy, 1 IP = 1 аккаунт | **MUST** | ✗ один статический прокси на всё |
| Согласованные IP/timezone/locale | **MUST** | ⚠ зависит от ручной настройки |
| Изоляция fingerprint per-account | **MUST** | ✗ общий браузер X+Threads |
| Человекоподобный rate-limit взаимодействий | **MUST** | ✗ сломан до 1/день (`02 R1`) |
| Cookie-first auth | nice→must | ✓ есть, но фолбэк на форму рискован |
| Re-login вне постинга, с cooldown | **MUST** | ✗ синхронно в постинге |
| Fallback-цепочки селекторов везде | nice | ⚠ только в постинге |
| Очистка скриншотов/профилей | nice | ✗ disk-leak |
| Шифрование сессий at rest | **MUST** | ⚠ DB — да, FB-профиль — нет (`04`) |
| DLQ-алерты | nice | ✓ Discord |
| Детекция шэдоубана/рестрикта | nice | ⚠ есть, но `networkidle`-баг |

## 8. Главная рекомендация раздела

Stealth browser-automation выбран намеренно — поэтому раздел про то, как его **закалить**, а не
сменить. Приоритет: верификация факта публикации (§2), идемпотентный ключ доменной операции + reaper
stuck-POSTING (§1), изоляция fingerprint/IP per-account и человекоподобные лимиты (§3). Это закрывает
бóльшую часть ban- и дубль-риска, не меняя подход.

Official API для **постинга** не используем — решение команды, путь stealth по всем сетям, включая
Threads/FB-Page (значит ban/SEC2-риск этих сетей остаётся на нас → та же дисциплина обвязки). Для
личного профиля FB API нет в принципе. Бесплатные **read**-API для метрик/аналитики — отдельная
история и допустимы (`05`).
