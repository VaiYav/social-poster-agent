# Module: `modules/content-source` + `infrastructure/content`

## 1. What this module does

`modules/content-source` is a thin facade over `IContentPort`. The actual content ingestion logic lives in `infrastructure/content` and is the starting point of the posting pipeline: it provides `ContentTopic` objects to `GenerationService`. The system can source topics from a sibling `content-agent-platform` (CAP) filesystem or from a DB-backed `Topic` table generated by `TopicGenerationService`.

**Main responsibilities:**
- `ContentSourceService` (`modules/content-source`) — delegates to `IContentPort`.
- `ContentReader` (`infrastructure/content`) — reads briefs, topic-queues, create-run reports, and blog articles from CAP filesystem.
- `DbContentReader` (`infrastructure/content`) — reads `Topic` rows from DB when CAP is unavailable.
- `TopicGenerationService` (`infrastructure/content`) — LLM-generated cron to keep the `Topic` pool filled.
- `ContentModule` (`infrastructure/content`) — selects between `ContentReader` and `DbContentReader` based on `CONTENT_AGENT_PLATFORM_PATH`.

## 3. How it works

### 3.1 `ContentSourceService`

A simple facade. The controller endpoints parse `limit` as integer and call the service.

### 3.2 `ContentModule` adapter selection

`useFactory`:
- If `CONTENT_AGENT_PLATFORM_PATH` is set and `join(capPath, 'runs')` exists → use `ContentReader` (filesystem).
- Else → use `DbContentReader` (DB).
- Exports both readers, `TopicGenerationService`, and `IContentPort`.

### 3.3 `ContentReader` (filesystem)

Reads from CAP repo structure:
- `readBriefs` — `runs/brief-*/brief.json` → `BriefSchema` (SERP-grounded, priority #1).
- `readCreateRuns` — `runs/create-*/report.json` → `CreateRunReportSchema` (fresh content, priority #2).
- `readTopicQueues` — `runs/topics-*/topic-queue.json` → `TopicQueueSchema` (ranked clusters, priority #3).
- `readArticles` — `content/blog/en/*.md` → `ArticleFrontmatterSchema` (fallback).

`getTopics(limit)` merges sources in priority order with a fallback cascade: briefs → create-runs → topic-queues → articles. It uses an in-memory LRU-style cache (one entry, by `limit`, TTL `CONTENT_CACHE_TTL_MS` default 2 min).

### 3.4 `DbContentReader` (DB)

- `getTopics` reads `prisma.topic` rows where `status: 'active'` ordered by `createdAt desc`.
- `readBriefs` and `readArticles` delegate to `getTopics`.
- `markUsed` sets a topic's status to `used` and `usedAt`. It is called by `GenerationService` after picking a topic? Wait, `DbContentReader` has `markUsed` but `ContentSourceService` doesn't expose it. `GenerationService` would need to call it via `IContentPort`? But `IContentPort` doesn't have `markUsed`. `DbContentReader` is exported by `ContentModule`, but `ContentSourceService` does not expose it. This means topics may be used repeatedly. **Potential issue**.

### 3.5 `TopicGenerationService`

- Cron registered in `onModuleInit` (unless `TOPIC_GENERATION_ENABLED=false` or orchestrator is enabled).
- Default cron `0 */2 * * *` (every 2 hours).
- On startup and on each cron, `generateIfNeeded()` checks active topic count.
- If `activeCount < TOPIC_POOL_MIN` (default 30), generates `TOPIC_BATCH_SIZE` (default 20) topics via `LlmService.generateChat`.
- Parses JSON array from LLM response using multiple strategies (direct parse, regex extraction, truncated repair).
- Deduplicates against existing topic strings (case-insensitive) and inserts new `Topic` rows.

### 3.6 `Topic` table (Prisma)

`Topic` has `id`, `topic`, `keywords`, `facts`, `category`, `sourceType`, `status` (`active`/`used`), `usedAt`, `createdAt`, `updatedAt`.

## 6. Findings

### 6.1 Bugs / correctness

**B1. `DbContentReader.markUsed` is not exposed through `ContentSourceService` or `IContentPort`**
- `db-content-reader.ts:58` has `markUsed` but `IContentPort` only has `getTopics`, `readBriefs`, `readArticles`. `ContentSourceService` only exposes those. `GenerationService` doesn't call `markUsed`. This means DB topics are never marked as used, so the same topic can be generated repeatedly. **Critical bug for DB mode.**

**B2. `ContentReader.getTopics` caches only by `limit`, not by source or time**
- `content-reader.ts:259` `if (this.topicsCache && Date.now() < this.topicsCache.expiresAt && this.topicsCache.limit >= limit)`. The cache stores `limit` and `topics`. If `limit` is 5 and later request is 10, it regenerates. If `limit` is 10 and later request is 5, it returns the cached 10-item list sliced to 5. Fine. But if the cache is for `limit=5` and a request for `limit=3` comes, it returns 3 cached items. Good. But if the cache is for `limit=10` and request is `limit=5`, it returns 5. But then `GenerationService` might later call `limit=3` and get 3. Good. But the cache has one slot, so it is invalidated on any `limit` greater than the cached one. Fine.

**B3. `ContentReader.getTopics` does not cache partial results? It caches only final result.**
- If briefs alone have `limit` items, it caches only briefs. Good.

**B4. `ContentReader.readBriefs` sorts directory names and reverses, but directory names like `brief-2026-07-01-abc` and `brief-2026-07-01-def` may not be sorted by time if names differ. It uses `fsStat` `mtime` for `publishedAt` but sorting is by name. If names are timestamps, it works. If not, it may not be newest first.**
- `content-reader.ts:52-57` sorts by name then reverse. CAP directory names may be `brief-2026-07-01-12-00-00` (timestamp). Good. But if names are slugs, not good.

**B5. `ContentReader.readBriefs` uses `limit * 2` for `slice` but the loop `if (topics.length >= limit) break` can stop before reading all `limit*2` directories. Good.**

**B6. `ContentReader.readBriefs` extracts `facts` from `parsed.outline.flatMap((o) => o.entities.slice(0, 3))`. This takes up to 3 entities per outline heading. For a brief with many headings, this could be many facts. `ContentTopic` type `facts` is `string[]`. Fine.**

**B7. `ContentReader.readArticles` uses `matter` but `matter` is imported as default `import matter from 'gray-matter'`. In ESM, `gray-matter` may have `default` export or `matter` named. Need to check. If it compiles, it's fine.**

**B8. `ContentReader.readCreateRuns` extracts topic from slug by capitalizing each word. This is heuristic and can produce weird topics for slugs like "2025-astro-forecast" → "2025 Astro Forecast". Acceptable.**

**B9. `ContentReader.getTopics` cache is not invalidated when new content appears on disk**
- `invalidateCache` is exported but not automatically called on file changes. The cache TTL handles staleness. Acceptable.

**B10. `ContentSourceController` parses `limit` with `Number.parseInt` without validation**
- `content-source.controller.ts:15` `return this.contentSourceService.getTopics(limit ? Number.parseInt(limit, 10) : 5);`. If `limit` is `'abc'`, `Number.parseInt` returns `NaN`, passed to `getTopics`. `getTopics` then uses `limit * 2` = `NaN`, `slice(NaN)`? Actually `slice(NaN)` is treated as 0. Then `limit` comparisons are false. Could cause reading all directories. Better to validate or default `limit` to a number.

**B11. `TopicGenerationService` parses JSON from LLM using regex and manual repair**
- `topic-generation.service.ts:149-190` This is fragile. The LLM prompt says "Return ONLY the JSON array, no markdown, no explanation" but still attempts multiple parse strategies. It would be better to use a structured output parser with `LlmService` or `zod` validation. But the current implementation is defensive.

**B12. `TopicGenerationService` `generateBatch` loads all existing topic strings into memory and deduplicates one by one in a loop**
- `topic-generation.service.ts:202-229` `const existing = await this.prisma.topic.findMany({ select: { topic: true }, where: {} })` loads **all** topic strings. If the table has 100k topics, this is a large memory load. Then it inserts one by one with `prisma.topic.create` in a loop. This is N+1 and not batched. Could use `createMany` and `skipDuplicates`.

**B13. `TopicGenerationService` `generateBatch` uses a `systemPrompt` string with user-facing prompt inside `LlmService.generateChat` (system + user). The prompt is embedded in the service. Good for now, but not Langfuse-managed. Not configurable without deploy.**

**B14. `TopicGenerationService` `onModuleInit` does `generateIfNeeded()` on startup even if orchestrator is enabled, then returns without registering cron**
- It does warm-up. If the orchestrator is supposed to handle topic generation, the startup warm-up could be okay. But `generateIfNeeded` may generate a batch immediately. Fine.

**B15. `TopicGenerationService` `generateBatch` returns `0` on parse failure. `generateIfNeeded` logs `Generating ${toGenerate} new topics` but if `generateBatch` returns 0, the pool stays low. The next cron (2 hours) will retry. Could be problematic if LLM consistently returns bad JSON.**

**B16. `ContentReader` `getTopics` uses `limit` type `number` but `ContentSourceController` passes `NaN` possible. `DbContentReader` uses `Number(limit) || 5`. `ContentReader` does not sanitize.**

**B17. `ContentReader` `readTopicQueues` and `readCreateRuns` log at `debug` level for missing runs dir, but `readBriefs` logs `warn`. Inconsistent. Not a bug.**

**B18. `ContentReader` `readArticles` uses `SITE_BLOG_PATH` default `../content/blog/en`. It ignores `language` and is hardcoded to English. Multilingual blog content is not supported.**

**B19. `DbContentReader` sets `language: 'en'` for all topics regardless of content. `ContentReader` also sets `language: 'en'`. Multilingual topics are not supported by content source.**

**B20. `ContentSourceService` does not expose `readTopicQueues`/`readCreateRuns`/`readCreateRuns` and `getTopics` uses priority logic hidden in `ContentReader`. The service is just a pass-through.**

**B21. `ContentModule` `useFactory` returns `fsReader` if `runs` dir exists, but if `fsReader` fails at runtime (e.g., permissions), it falls back to `dbReader` only at module init based on existence. It doesn't catch runtime failures.**

### 6.2 Performance

**P1. `ContentReader` reads disk synchronously-ish (async `fs/promises`) for every `getTopics` call unless cached**
- With cache TTL 2 minutes, it reads disk on cache miss. For generation cron every 2 hours, this is fine. For manual API calls, it may be slow.

**P2. `ContentReader` `readBriefs` reads `brief.json` and does `fsStat` per brief. For `limit*2` directories, this is `limit*2` reads. Fine for small `limit`.**

**P3. `TopicGenerationService` loads all topic strings into memory**
- As noted, `findMany` without `take` loads all. This is a memory/time hot spot for large `Topic` tables.

**P4. `TopicGenerationService` inserts one by one**
- Use `createMany` with `skipDuplicates`.

**P5. `DbContentReader` `getTopics` does `Number(limit) || 5` which is safe for `NaN` (returns 5). But `ContentReader` does not. Inconsistent.**

### 6.3 Architecture / anti-patterns

**A1. `ContentSourceService` is a trivial pass-through and could be folded into `ContentModule` or `IContentPort` directly**
- It exists to provide a module-level service for `GenerationService` to inject. Acceptable.

**A2. `DbContentReader` `markUsed` not in `IContentPort` is an architectural gap**
- The port should have `markUsed` or the `ContentSourceService` should expose it. Otherwise, DB mode can't track used topics.

**A3. `TopicGenerationService` is in `infrastructure/content` but uses `LlmService` directly. It should depend on `ILlmPort`?**
- `LlmService` is the implementation. `LlmModule` may bind `ILlmPort` to `LlmService`. The service uses `LlmService` directly. This is a concrete dependency. Not a critical issue since `LlmService` is the only adapter.

**A4. `ContentReader` and `DbContentReader` both have `language: 'en'` hardcoded**
- Multilingual content source is not supported. `GenerationService` rotates `POSTING_LANGUAGES` but the source is always English.

**A5. `ContentModule` exports both `ContentReader` and `DbContentReader` and `TopicGenerationService` — too many exports**
- Only `IContentPort` and `TopicGenerationService` should be exported. The readers are internal to the module. But exporting them is useful for tests and direct injection. Not a bug.

**A6. `TopicGenerationService` prompt is embedded and not in Langfuse**
- The project uses Langfuse for production prompts. This prompt should be in Langfuse for versioning and A/B testing. Currently hardcoded.

### 6.4 TypeScript / type safety

**T1. `ContentSourceController` `limit?: string` and `Number.parseInt` without validation. Could use `ParseIntPipe`.**

**T2. `ContentReader` `getTopics` returns `Promise<ContentTopic[]>` and uses `ContentTopic` from `@spa/shared`. Good.**

**T3. `TopicGenerationService` `LlmTopic` interface is inline. Could be a shared schema.**

**T4. `TopicGenerationService` `generateChat` response is `response.content` string. It doesn't use `response.content` as an array. Good.**

### 6.5 Security / reliability

**S1. `ContentSourceController` endpoints can be called by any authenticated user. If `AUTH_ENABLED=false`, pass-through. Reading content topics is not sensitive. Fine.**

**S2. `ContentReader` reads arbitrary filesystem paths from `CONTENT_AGENT_PLATFORM_PATH` and `SITE_BLOG_PATH`. If an attacker can set env vars, they could read arbitrary directories. But env is trusted. In `browser.factory`, `user_data_dir` etc. are also env-driven. Fine.**

**S3. `ContentReader` `readCreateRuns` parses `report.json` from disk and uses `parsed.files[0]` to build a topic. If `files` contains a path like `../../../etc/passwd`, the slug extraction is safe (just string manipulation). But if `parsed.files` is not validated, `firstFile.split('/').pop()` could be anything. No path traversal. Fine.**

**S4. `TopicGenerationService` prompt injection risk? The prompt is static. The `count` is from config. Fine.**

**S5. `TopicGenerationService` `generateBatch` does not catch and log individual `prisma.topic.create` errors beyond `for` loop. It catches only at top. `prisma.topic.create` may throw if a unique constraint on `topic` exists? If `topic` has unique index, the `existingSet` check prevents duplicates but is race-prone. `createMany` with `skipDuplicates` would be safer.**

## 7. New feature / improvement ideas

**F1. Add `markUsed` to `IContentPort` and `ContentSourceService`**
- Fix the DB mode topic reuse bug.

**F2. Use `createMany` with `skipDuplicates` in `TopicGenerationService`**
- Performance and race safety.

**F3. Move `TopicGenerationService` prompt to Langfuse**
- Versioning and A/B testing.

**F4. Add per-language content source paths**
- `SITE_BLOG_PATH_{lang}` or `content/blog/{lang}`. `ContentReader` should support language-specific directories.

**F5. Add `ContentSourceController` input validation for `limit`**
- Use `ParseIntPipe` or Zod.

**F6. Add `ContentReader` cache invalidation endpoint or file watcher**
- For manual refresh or immediate content updates.

**F7. Add `Topic` table pagination in `TopicGenerationService`**
- Don't load all topic strings into memory.

**F8. Add `Topic` table `language` column and support non-English topics**
- Generate topics in `POSTING_LANGUAGES`.

**F9. Add content-source metrics**
- `topics_available`, `topics_used`, `briefs_read`, `topic_generation_success_rate`, `topic_pool_size`.

**F10. Add `TopicGenerationService` fallback to filesystem if DB is empty and CAP is available?**
- `ContentModule` already selects one adapter at startup. `TopicGenerationService` is DB-only. If `ContentReader` is used, `TopicGenerationService` is not needed. If `DbContentReader` is used, `TopicGenerationService` fills the pool. Good.

**F11. Add `ContentSourceService` method `markUsed` and call it from `GenerationService`**
- This is the most important fix.

**F12. Add `ContentSourceService` `invalidateCache` method and controller endpoint**
- For ops to refresh topics.

## 9. Overall assessment

- **Health**: 6/10. The module is clean but has a critical bug (`markUsed` not exposed for DB mode), prompt hardcoding, and `TopicGenerationService` dedup inefficiency.
- **Biggest strengths**: hexagonal `IContentPort`, auto-detection of CAP vs DB, multi-source priority fallback in `ContentReader`, `TopicGenerationService` DB-backed self-contained mode.
- **Biggest risks**: `DbContentReader.markUsed` never called → topics reused; `TopicGenerationService` loads all topic strings into memory and inserts one by one; hardcoded English-only content; prompt not in Langfuse; `ContentSourceController` `limit` not validated.
- **Recommended next actions**:
  1. Add `markUsed` to `IContentPort` and call it from `GenerationService`.
  2. Use `createMany` with `skipDuplicates` in `TopicGenerationService`.
  3. Move `TopicGenerationService` prompt to Langfuse.
  4. Validate `limit` in `ContentSourceController`.
  5. Add language-aware content source paths.
